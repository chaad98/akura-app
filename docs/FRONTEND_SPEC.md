# Frontend Spec — akura-app

Next.js (App Router) + TypeScript + Tailwind CSS v4.
Talks to `akura-api` over HTTP. No database access in this repo.

---

## 1. The rendering strategy

Akura has two halves with opposite requirements. Treating them the same is the main
thing to avoid.

| Half | Pages | Rendering | Why |
|---|---|---|---|
| **Public** | `/`, `/pricing`, `/how-it-works` | **SSG** — static at build time | Google indexes these; they must be fast and crawlable |
| **App** | `/login`, `/dashboard`, `/project/[id]` | **CSR** — client components fetching from the API | Behind auth, never indexed, personalised per user |

**Why the app half is not SSR.** Server-rendering an authenticated page means
browser → Vercel → `api.akura.my` → back, adding a network hop per navigation, with
Vercel and Railway potentially in different regions. SSR's benefits — SEO and
content-in-first-paint — don't apply to a page only one logged-in person ever sees.
CSR with a proper loading state is simpler and usually faster in practice here.

**Where Server Components still earn their place:** static layout shells, the public
pages, and anything with no per-user data. Use them freely there; they ship zero JS.
Just don't reach for server-side data fetching on authenticated views.

If a public page later needs frequently-changing content, ISR (`revalidate`) is the
next step — still not per-request SSR.

## 2. SEO — public pages only

This is where SEO effort goes. Authenticated pages must **not** be indexed.

- Per-page `metadata` exports: title, description, canonical URL, Open Graph and
  Twitter tags. Write these for a Malaysian renovation contractor searching for a way
  to stop arguing with clients over WhatsApp — not for generic "project management".
- `app/sitemap.ts` and `app/robots.ts` (both TypeScript, both generated by Next.js).
- `robots.ts` must **disallow** `/dashboard`, `/project/`, and `/login`.
- Set `metadataBase` so relative OG image URLs resolve.
- JSON-LD `SoftwareApplication` structured data on the landing page.
- `next/image` for any hero imagery, `next/font` for fonts — both prevent layout shift,
  which is a ranking factor.
- Semantic HTML: one `<h1>` per page, real heading hierarchy, descriptive link text.

**Performance targets** for the public pages: LCP under 2.5s, CLS under 0.1. Static
generation plus `next/image` and `next/font` gets you there without special effort.

## 3. Tailwind CSS v4 — setup differs from older guides

v4 is CSS-first. Anything referencing `tailwind.config.js` or `@tailwind base;` is
v3-era and does not apply.

- **No `tailwind.config.ts`.** Content paths are auto-detected. Do not create one.
- `app/globals.css` begins with a single import:
  ```css
  @import "tailwindcss";
  ```
- Theme customisation lives in CSS:
  ```css
  @theme {
    --color-brand: oklch(0.55 0.15 250);
    --font-sans: "Inter", sans-serif;
  }
  ```
- Next.js still needs a thin `postcss.config.mjs` listing `@tailwindcss/postcss`.
  **Do not add `autoprefixer`** — v4 prefixes internally and keeping it causes
  double-prefixed output.

Scaffold with `create-next-app --tailwind` to get this wired correctly.

## 4. Type safety

**TypeScript only.** No `.js` / `.jsx`. Rename the generated `next.config.js` to
`next.config.ts` and type it with `NextConfig`.

Unavoidable non-TS files: `package.json`, `tsconfig.json`, `.eslintrc.json`,
`postcss.config.mjs` (PostCSS has no TS config support), generated `next-env.d.ts`.

**`any` is banned** outside test files. Enforce structurally:

```json
// tsconfig.json
{ "strict": true, "noImplicitAny": true, "noUncheckedIndexedAccess": true }
```
```json
// .eslintrc.json
{
  "rules": { "@typescript-eslint/no-explicit-any": "error" },
  "overrides": [{
    "files": ["**/*.test.ts", "**/*.test.tsx"],
    "rules": { "@typescript-eslint/no-explicit-any": "off" }
  }]
}
```

`strict` catches implicit `any`; the ESLint rule catches explicit `any`. Use `unknown`
plus narrowing where a shape genuinely isn't known — `any` disables checking,
`unknown` forces you to prove the shape.

### `lib/types.ts`

The backend is a separate repo with no shared package, so this repo declares its own
types mirroring the API responses:

```ts
export type Role = 'CONTRACTOR' | 'CLIENT';
export type StageStatus = 'PENDING' | 'IN_PROGRESS' | 'COMPLETED' | 'BLOCKED';
export type ApprovalStatus = 'PENDING' | 'APPROVED' | 'DECLINED';

export interface User { id: string; email: string; name: string; role: Role }

export interface Stage {
  id: string; projectId: string; title: string; status: StageStatus;
  note: string | null; photoUrl: string | null;
  createdAt: string; updatedAt: string;        // ISO 8601 UTC
}

export interface Approval {
  id: string; projectId: string; title: string; description: string;
  costCents: number;                            // integer cents
  status: ApprovalStatus;
  createdAt: string; decidedAt: string | null;
}

export interface Project {
  id: string; name: string; contractorId: string; clientId: string; createdAt: string;
}

export interface ProjectDetail extends Project {
  stages: Stage[]; approvals: Approval[];
}

export interface Paginated<T> { items: T[]; page: number; limit: number; total: number }
```

Hand-syncing this with the backend is the real cost of separate repos. When a response
shape changes, update this file in the same sitting — a stale type compiles fine and
fails at runtime.

Dates arrive as ISO strings, not `Date`. Type them `string`, convert at display time.

### Where `any` tries to sneak in

- `useState<any>(null)` → `useState<ProjectDetail | null>(null)`, handle the null branch
- Event handlers → `React.FormEvent<HTMLFormElement>`,
  `React.ChangeEvent<HTMLInputElement>`
- Caught errors → `unknown` under `strict`; narrow with `instanceof Error`
- Select values → write a type guard rather than `as Role`, so a typo fails loudly

## 5. API client (`lib/api.ts`)

One module wrapping `fetch`. No scattered `fetch` calls in pages.

**`credentials: 'include'` on every single request.** This is the most common failure
mode: without it the cookie is never sent and every authenticated call 401s while the
code looks correct.

Make it generic so `res.json()`'s `any` never escapes:

```ts
async function request<T>(path: string, options: RequestInit = {}): Promise<T> {
  const res = await fetch(`${API_URL}${path}`, {
    ...options,
    credentials: 'include',
    headers: { 'Content-Type': 'application/json', ...options.headers },
  });
  if (!res.ok) {
    const body: unknown = await res.json().catch(() => ({}));
    throw new Error(extractMessage(body) ?? `Request failed: ${res.status}`);
  }
  return res.json() as Promise<T>;
}
```

| Method | Calls | Returns |
|---|---|---|
| `register(data)` | `POST /auth/register` | `User` |
| `login(data)` | `POST /auth/login` | `User` |
| `logout()` | `POST /auth/logout` | `void` |
| `me()` | `GET /auth/me` | `User` |
| `listProjects(page?)` | `GET /projects` | `Paginated<Project>` |
| `createProject(data)` | `POST /projects` | `Project` |
| `getProject(id)` | `GET /projects/:id` | `ProjectDetail` |
| `createStage(projectId, data)` | `POST /projects/:projectId/stages` | `Stage` |
| `updateStage(projectId, stageId, data)` | `PATCH /projects/:projectId/stages/:stageId` | `Stage` |
| `createApproval(projectId, data)` | `POST /projects/:projectId/approvals` | `Approval` |
| `decideApproval(approvalId, decision)` | `PATCH /approvals/:approvalId` | `Approval` |

`decideApproval` is **flat**, not nested under a project. Match the backend exactly.

## 6. Auth handling

The token lives in an httpOnly cookie the browser attaches automatically. There is
nothing to store, read, or send manually.

- Never touch `localStorage` or `sessionStorage`
- Never set an `Authorization` header
- Never expect `accessToken` in a response body — if you find yourself reaching for it,
  the backend is misconfigured

**`GET /auth/me` is the only way to know who is logged in.** An `AuthContext` calls it
once on mount and exposes `user`, `loading`, `refresh()`, `logout()`. Render a loading
state during that first call, or protected pages flash their empty state.

**Logout is a server call** — the client cannot delete an httpOnly cookie.

### Route protection

`middleware.ts` redirects to `/login` when the `access_token` cookie is **absent** on
`/dashboard` and `/project/*`. This is a UX convenience only — middleware checks
presence, not validity, and cannot verify the signature. **The backend is the actual
gate.** Never rely on middleware or conditional rendering for security.

## 7. Pages

| Route | Rendering | Purpose |
|---|---|---|
| `/` | SSG | Landing — the problem, the product, a call to action |
| `/pricing` | SSG | Optional for v1 |
| `/login` | CSR | Register or log in, choosing contractor or client |
| `/dashboard` | CSR | Project list; create-project form (contractor only) |
| `/project/[id]` | CSR | The shared view: stage checklist + approvals |

App pages need `'use client'`. Public pages should stay Server Components.

### `/login`
One page, a `mode` toggle between login and register. Register adds name and a role
select labelled in plain language ("I'm a contractor" / "I'm a client"). On success the
cookie is set server-side — refresh the auth context, then route to `/dashboard`.

### `/dashboard`
Fetches `listProjects()`. The backend filters by role, so both roles use the same call.
Empty state when there are none. Create-project form shown only when
`user.role === 'CONTRACTOR'`. Note the client must already have an account or the API
returns 404 — say so in the placeholder.

### `/project/[id]`
One `getProject(id)` call returns stages and approvals nested.

**Stages** — list with title and status; status buttons and an add-stage form for the
contractor.

**Approvals** — list with title, cost, status, description. Approve/decline buttons
only while `PENDING`, and they disappear once decided; a settled decision must not look
re-clickable. Raise-VO form for the contractor.

**Money conversion:** sending `Math.round(Number(rm) * 100)`, displaying
`(costCents / 100).toFixed(2)`. Get this wrong and RM 3,200 bills as RM 3.20.

**After any mutation, re-fetch.** Simple and always correct at this scale.

## 8. Security in this repo

The frontend's job is narrow but the rules are absolute.

- **No secrets, ever.** No `DATABASE_URL`, no API keys, no Prisma. Anything with a
  `NEXT_PUBLIC_` prefix is visible in the browser bundle — only `NEXT_PUBLIC_API_URL`
  belongs there.
- **No database access.** All data goes through `api.akura.my`, which owns the domain
  rules, authorization, and logging. Direct Postgres access from here would bypass all
  of them.
- **Role-based rendering is UX, not security.** Hide controls a role can't use, but
  assume anyone can call the API directly.
- **Never render raw HTML from API data.** No `dangerouslySetInnerHTML` — project
  names and VO descriptions are user input. React escapes by default; don't opt out.
- Keep `NEXT_PUBLIC_API_URL` pointed at `https://api.akura.my` in production so the
  cookie's `sameSite: 'lax'` and `.akura.my` domain both apply.

## 9. Environment

```
NEXT_PUBLIC_API_URL=http://localhost:3001    # https://api.akura.my in production
```

The `NEXT_PUBLIC_` prefix is required for browser access — without it the value is
server-only and fetches hit `undefined`. It must match the backend's
`FRONTEND_ORIGIN` CORS setting, and in production both apps sit on subdomains of
`akura.my` so the session cookie stays `sameSite: 'lax'`.

## 10. Out of scope for v1

Photo upload UI, a component library or design system, optimistic updates, refresh
token handling, dark mode, i18n. Style with Tailwind utilities directly — don't build
abstractions over them yet.

## 11. Acceptance checklist

### Rendering and SEO
1. `/` is statically generated — confirm in the build output.
2. `view-source:` on `/` shows the marketing copy in the HTML, not an empty div.
3. `/robots.txt` disallows `/dashboard`, `/project/`, `/login`.
4. `/sitemap.xml` lists only public pages.
5. Lighthouse on `/`: Performance and SEO both 90+.

### Auth
6. Register → redirected to dashboard with name and role shown.
7. DevTools → Application → Cookies: `access_token` present, **HttpOnly** ticked.
8. Console: `document.cookie` does **not** show `access_token`.
9. Hard refresh the dashboard → still logged in.
10. Logout → `/dashboard` redirects to `/login`.
11. Visiting `/dashboard` logged out → redirected, no flash of content.

### Core flow (two browser profiles — normal plus incognito)
12. Contractor creates a project with the client's email.
13. Client logs in and sees the same project.
14. Contractor adds a stage, marks it `COMPLETED`; the client sees it.
15. Contractor raises a VO for RM 3,200 → displays as `3200.00`.
16. Client approves → status updates; buttons disappear.
17. Contractor refreshes → sees `APPROVED`.

### Type safety
18. `npm run build` passes with no type errors.
19. `grep -r ": any" app/ lib/` finds nothing outside test files.

> Use a normal window plus incognito rather than two tabs — cookies are shared across
> tabs of one profile, so both tabs would be logged in as whoever authenticated last.
